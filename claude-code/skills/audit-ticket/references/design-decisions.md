# audit-ticket — design decisions

Decisions taken while designing the `audit-ticket` skill. Dated 2026-11-10.

| # | Decision | Why |
|---|---|---|
| D1 | The skill is named `audit-ticket`. | Its scope is wider than docs: tasks, progress, checklists, acceptance criteria, and Jira. |
| D2 | Redesign the ticket workspace so each fact lives in one file only. Do not audit the current overlapping layout as-is. | The layer review found the same fact in several files that disagree. Evidence: a layer-by-layer review of real ticket workspaces (kept in the host repo, not here). |
| D3 | The layout redesign goes in the sdlc plugin (`plugins/sdlc`). The skill is user-level, at `claude-code/skills/audit-ticket` (linked as `~/.claude/skills`). It was moved out of the host repo on 2026-11-10. | The layout comes from the plugin's contracts, so it is fixed there. A user-level skill serves every repo. Tracker scope: D7. |
| D4 | Proposed agents (not final): `ticket-jira-snapshot` (lookup tier), `ticket-local-snapshot` (lookup tier), `ticket-code-auditor` (implementation tier, one per slice). Alignment and reconcile run inline (reasoning tier). | Agents that only read get the cheap tier. The code check is per slice, so it can run in parallel. Judging across sources needs the reasoning tier. Each model is set through `metadata.model-tier`, never by name (`ai-models.json`). |

| D5 | Revised on 2026-11-10. Design the target layout and the skill together in this session. The sdlc plugin change follows later, from this log. | The user wants the skill generated now. Settling the layout here first still avoids rework. |

| D6 | Target workspace, one owner per fact. Jira: slices, sub-task state, ACs, Blocks links. `state.json` `units[]`: branch, MR, readiness. `prd.md`: tagged copy of the Jira ACs. `decisions.md`: every decision, D-numbered, with `replaces`. `spec.md`: design only. `issue-graph.md`: slice ↔ key and edges, no state. `tasks/issue-<N>/step-*.plan.md`: scope, `depends_on`, `jira:`, `Done when` boxes. `tasks/issue-<N>/progress.md`: step status and the AC → step coverage table. Removed: `3-plan.md`, `N-plan.md`, `N-progress.md`, `pipeline.md`, `jira-snapshot.md`, `t*/` sub-workspaces. | the layer review (§8, kept in the host repo). Checkboxes live only in `Done when` and the coverage table, so the auditor has one place to tick each. |
| D7 | Tracker calls come from each repo's `docs/agents/issue-tracker.md` and `ticket-tracker.md`. The skill has no tracker-specific calls. If those docs are missing, it stops and asks. | It serves Jira and GitHub repos without carrying both call sets. Same pattern as the sdlc skills. |
| D8 | The agents are user-level and set `model:` directly: the snapshot agents use `haiku`, `ticket-code-auditor` uses `sonnet`. Alignment and reconcile run in the main session (Opus). This replaces the tier wording in D4. | `ai-models.json` exists only in the host repo. Existing user-level agents already use `model:`. |
| D9 | Jira writes are transitions only, each approved by the user and picked by target status name. No labels, comments, new sub-tasks or description edits. Any other Jira mismatch becomes a question, and the user acts on Jira. | User choice. It keeps the skill's remote footprint minimal. |
| D10 | Every local fix gets its own approval question with its evidence: a box tick, a status flip, a `state.json` edit. Nothing is applied in a batch or automatically. | User choice. Accepted cost: big tickets (one real ticket had about 60 stale boxes) produce many questions. |
| D11 | A step or AC is "done" only when all four hold: (1) its files changed in `git diff origin/<default>...HEAD` and match `Done when`; (2) a branch commit carries its key; (3) a spec covering it is in the diff; (4) that spec passes. Test runs follow the never-run-unprompted rule: the auditors only list the specs, then the skill asks once and runs every listed spec in one scoped command. If you decline, missing signal (4) gives the verdict `partial`, never `done`. | User choice: all four signals. The test run stays under the user's control. |
| D12 | `audit-ticket` takes over `organize-ticket-docs` as its first phase, "normalize layout". The old skill was deleted on 2026-11-10, after the user approved. Its rules carry over: git check, delete only on yes, never commit, never touch source. `audit-docs` stays separate, for docs outside tickets. | User choice: one skill for the whole ticket workspace. |
| D13 | Normalize migrates any workspace that is off D6: no `state.json`, a schema below v5, duplicate plan or progress files, `t*/` sub-workspaces. Each move, merge or schema bump is one question with its evidence. The audit runs only after normalize. | One layout means one audit path. Asking per change matches D10. |
| D14 | Overlap. Absorbed: `organize-ticket-docs` (phase 1). Delegated: archiving to `doc-archiver` (phase 7). Not reused: `code-review:spec-reviewer`, which needs the review contract and `gh` and returns findings rather than step verdicts (its fix-side idea is copied). `karen` has no Bash, so no git. `qa-ready`/`cr-ready` add labels, which D9 forbids. `audit-docs` stays for non-ticket docs. | Survey of user-level and sdlc skills and agents on 2026-11-10. |
| D15 | Mechanical work is done by scripts: `snapshot-local`, `git-evidence`, `align`, `apply-fix`, `view`. This replaces the local-snapshot agent from D4/D8. The agents are `ticket-tracker-snapshot` (haiku; renamed from `ticket-jira-snapshot` per D7) and `ticket-code-auditor` (sonnet, ≤4 steps each, parallel). The main session reads only `view.mjs` lines. | Parsing, diffing and comparing are deterministic, so they cost zero tokens. Models are spent only on judgment. |
| D16 | The skill runs on `model: sonnet`, replacing Opus from D8. For a messy migration, the user switches to Opus with `/model`. | After D15, the session judges only short script output. D10/D13 mean dozens of turns per ticket, and Sonnet costs roughly 1/5 of Opus per turn. |
| D17 | Replaces D10. Fixes the code and commits back are applied without a question and logged in `applied.jsonl`: box ticks, status flips, stale doc lines. Questions are only for ambiguity, a conflict, a delete that is not provably dead, a tracker transition, or a scope call. | The user, during the first run on PROJ-123 (2026-11-10): asking to confirm evidence-backed ticks is noise, because the user has no context of the work. The skill holds the evidence. |
| D18 | Epic layout is accepted next to D6: slice folders `t<N>-<key>-<slug>/` under an epic root, each with its own `state.json`, `spec.md`, `tasks/step-*.plan.md` and `tasks/progress.md` (no `issue-<N>/` level). `prd.md` and `decisions.md` stay at the root. Migration and the audit run at the root level and at each slice level. Not flattened. Partly replaces the `t*/` rule in D6 and D13. | The user, on PROJ-456 (2026-11-11): the org also accepts several linked tickets under one epic. Flattening would erase the per-ticket planning folders. `snapshot-local.mjs` encodes it (`epicSlices`, `isSlice`). |
